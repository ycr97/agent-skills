# Skill Authoring Guide

## 1. Definition

A skill is a self-contained directory whose entry point is `SKILL.md`. It encodes reusable instructions and may include supporting references, scripts, assets, and examples.

This repository follows the portable core of the Agent Skills convention:

```text
<skill-name>/
├── SKILL.md            # required
├── references/         # optional
├── scripts/            # optional
├── assets/             # optional
└── examples/           # repository convention; optional
```

## 2. Naming

Use lowercase kebab-case:

```text
first-principles-learning
root-cause-debugging
architecture-review
```

The directory name MUST match the YAML `name` value.

## 3. Frontmatter

Minimum:

```yaml
---
name: root-cause-debugging
description: Diagnose software or infrastructure failures by establishing evidence, isolating the failing layer, testing hypotheses, and identifying the root cause before changing behavior. Use when the user asks to debug, investigate, or explain a failure. Do not use for simple syntax questions with an already-obvious fix.
---
```

### Description quality

The description is discovery metadata, not marketing copy. It should answer:

- What capability does this skill provide?
- When should an agent consider it?
- What important boundary prevents false activation?

Put high-value trigger semantics early because hosts may truncate long skill descriptions when many skills are installed.

## 4. `SKILL.md` content

Prefer operational guidance:

- objective,
- activation boundaries,
- execution process,
- branching/diagnosis rules,
- completion criteria,
- links to references.

Avoid putting long background essays directly in `SKILL.md` if they can be loaded on demand.

## 5. Progressive disclosure

Use supporting files when they improve focus:

- `references/`: methodology, domain knowledge, detailed policies, rubrics.
- `scripts/`: deterministic/repeated operations that should not be regenerated by the model.
- `assets/`: templates or reusable static resources.
- `examples/`: activation cases, expected behavior, evaluation scenarios.

A host should be able to discover a skill from `name` + `description`, then read `SKILL.md`, then load only the additional resources required by the current task.

## 6. Agent portability

The skill itself should not hard-code local installation paths or assume one specific agent unless that dependency is fundamental to the capability.

Keep installation/discovery paths in repository-level integration docs and scripts.

If an agent requires genuinely different runtime behavior, prefer a small adapter or explicit dependency section rather than copying the whole skill.

## 7. Completion criteria

A skill should state what "done" means. This prevents workflows from degrading into generic advice.

Examples:

- debugging skill: root cause is supported by evidence and remediation addresses that cause;
- review skill: identified findings are tied to concrete code or requirements;
- learning skill: the learner demonstrates application and transfer rather than recognition alone.

## 8. Evaluation before promotion

Before marking a skill stable, test at least:

- one obvious activation case,
- one ambiguous activation case,
- one non-activation case,
- one normal successful workflow,
- one failure/uncertainty path.

Store representative cases under `examples/` when they add long-term value.
